## 1. Project Overview

- **Project name:** Obsidian Live Share — Canvas Integrity Round
- **Target vision:** Make the multiplayer Obsidian canvas trustworthy: remote cursors land where the peer's pointer is, a held card cannot be overwritten, every remote change reaches the open view, presence survives a background window, and each `.canvas` file has exactly one writer.
- **Primary user group / consumers:** Two or more Obsidian users sharing a vault over the `liveshare-relay`, editing the same `.canvas` file concurrently. Secondary consumer: the maintainer diagnosing a reported drift incident from a log dump.
- **Non-goals:**
  - Enabling, changing or repairing the `useCanvasBinding` path. It stays **OFF and dormant** (PLAN D1). Its `{id}`-edge-capture data-loss defect is a documented **rollout blocker**, not a work item — see § 12 R1.
  - Proving S2's root cause. This round guards it defensively and instruments it (PLAN D3). Diagnosis may remain open.
  - Any change to `server/`, the deploy stack, `docker/.env`, or the plugin version (`0.6.0`).
  - Dropping `"canvas"` from `TEXT_EXTENSIONS` (ARCHITECTURE Option 2) or making a canvas the active-file owner (Option 3). Both were considered and rejected: Option 2 reroutes canvases through binary transfer via `plugin/src/files/manifest.ts:75` and `plugin/src/files/file-ops.ts:384`/`:416`; Option 3 relies on a guard designed for the focused editor and leaves a background-tab canvas double-syncing.
  - Mass reformatting. ~93 pre-existing biome findings on untouched files stay.
- **UI language / locale:** English (code, comments, log lines). No user-facing copy changes in scope.

### Key architecture decisions

- **D1 — `useCanvasBinding` stays OFF and dormant.** Only the legacy `CanvasSync` path is repaired. *Why:* the binding path carries an unfixed data-loss defect (§ 12 R1); repairing two paths at once doubles the blast radius of a round that already touches five files.
- **D2 — the cursor fix lives in the adapter, not at the call sites.** *Why:* `plugin/src/canvas/canvas-presence.ts:485` and `:493` stay untouched, which keeps WP1/WP3 file-disjoint from WP4/WP5 and lets Batch A and Batch C run concurrently. Correcting the transform in one place also fixes `clientToCanvas`'s manual fallback for free.
- **D3 — S2 is guarded defensively *and* instrumented; no AC claims diagnosis.** *Why:* all three candidate mechanisms (awareness prune, latched `isDragging`, patch-less second adapter) are cheap to make structurally impossible, and none is proven. Acceptance is phrased as "structurally impossible" or "observable in the log" (US4 preamble).
- **D4 — WP6 (exclusion) is a hard prerequisite of WP7 (persistence), not an alternative.** *Why:* single-writer semantics are unreachable while `BackgroundSync` still holds a second `Y.Text` document for the same path and writes it. Wiring `CanvasPersistence` first would produce three writers, not one.
- **D5 — red-first for every defect fix** (`w4_fix_as_failing_test: true`). *Why:* four of the seven WPs fix behaviour that the existing suite either does not cover (WP6: no test wires both subsystems to one path) or actively asserts as correct (WP1: four tests). A green-only fix is indistinguishable from no fix.
- **D6 — every non-trivial decision procedure is extracted as a pure exported function.** *Why:* `plugin/src/main.ts` has **no test file** (32 test files, none for `main.ts`), and `reconcileLiveCanvas` / the ownership predicate are the two places where this round's logic would otherwise be untestable. This is the existing house pattern — `computeCanWriteNode`, `resolveHolder`, `resolveCursors`, `canvasToScreenRel` are all already pure and unit-tested.
- **D7 — ownership is exclusive, not layered.** A shared `.canvas` path is owned by `CanvasSync` **or** by `BackgroundSync`, never both, and never neither while it is shared. See § 6 for the state machine. *Why:* "single writer" is unenforceable as a per-write check; it is enforceable as a per-path ownership invariant with two explicit transitions.

## 4. Data Architecture

- **Primary data sources:** the `.canvas` JSON file on disk; the per-path Yjs documents on the relay; the per-path Yjs **awareness** channel (cursors + locks).
- **Core data models:**

```text
.canvas file (JSON)
├── nodes[]  ← id, type ("file"|"text"|"link"|"group"), x, y, width, height, + type-specific
└── edges[]  ← id, fromNode, toNode, fromSide, toSide, + optional color / label

Y.Doc "__canvas__:<path>"                    owner: CanvasSync (+ CanvasPresence on .awareness)
├── nodes : Y.Map<id, Y.Map<field, primitive>>
└── edges : Y.Map<id, Y.Map<field, primitive>>

Y.Doc "<path>"                               owner: BackgroundSync  ← THE DEFECT
└── content : Y.Text  (the same file, as one raw JSON string)
```

  Array→map conversion happens in `parseCanvas` (`plugin/src/files/canvas-sync.ts:43-62`): entries without an `id` are silently dropped and a parse failure yields empty maps rather than throwing.
- **Normalisation rules:** paths are canonicalised through `toCanonicalPath(normalizePath(p))` at every subsystem boundary; disk paths through `toLocalPath(p)`. Serialization is always `JSON.stringify(buildCanvasData(...), null, "\t")` so both writers would produce identical bytes.
- **Consistency and integrity rules** (application-level — Yjs guarantees convergence, not semantic validity):
  - No dangling edge is ever serialized: `buildCanvasData` drops an edge whose `fromNode`/`toNode` names an absent node (`plugin/src/files/canvas-sync.ts:88-96`). **Known hole:** the guard requires a `string`, so an edge that *lost* the key entirely passes through.
  - Deleting a node cascade-prunes its edges in the CRDT (`:603-618`).
  - `x/y/width/height` are undeletable (`:155`, `:192`). WP5 adds `type`.
  - Delete-wins / no-resurrect for nodes (`:575-580`). WP4 extends it to edges.
- **Data flow, flag OFF (production), after this round:**

```text
local edit ──► .canvas on disk ──► vault-events (ownership gate, WP6)
                                     ├── canvas-owned ──► CanvasSync.handleLocalModify ──► Y.Maps
                                     └── not owned    ──► BackgroundSync.handleLocalTextModify ──► Y.Text
remote Δ  ──► doc observer ──► reconcileLiveCanvas (WP5 classifier) ──► open canvas view
Y.Maps    ──► CanvasPersistence (WP7, sole writer) ──► .canvas on disk ──► CanvasSync.lastWrittenContent
awareness ──► CanvasPresence ──► locks (WP4 gates) + cursors (WP1 transform) ──► overlay
```

### 6.1 Canvas ownership state machine (WP6 — resolves PLAN open question 1)

```text
                 ┌──────────────────────── shared .canvas path ────────────────────────┐
                 │                                                                     │
   ┌─────────────▼──────────────┐   subscribe() invoked (sync, :324)   ┌────────────────▼─────────────┐
   │ TEXT-OWNED (fallback)      │ ───────────────────────────────────► │ CANVAS-OWNED                 │
   │ BackgroundSync holds Y.Text│   preceded by backgroundSync         │ CanvasSync holds nodes/edges │
   │ warn CANVAS TEXT FALLBACK: │      .unsubscribe(path)              │ text path unreachable        │
   └─────────────▲──────────────┘ ◄─────────────────────────────────── └──────────────────────────────┘
                 │                  subscribe() settled AND
                 │                  isSubscribed(path) === false
                 │                  → backgroundSync.subscribe(path)
                 └── entered only on a FAILED subscribe (getDoc null :328-330, or waitForSync throw :335-337)
```

- **Predicate:** `canvasOwned(path) === path.endsWith(".canvas") && !!canvasSync && canvasSync.isSubscribed(path)`. Evaluated once per `modify` event.
- **Invariant:** exactly one owner while the path is shared. `canvasOwned` true ⇒ `handleLocalTextModify` is unreachable for that path, whatever the reason the canvas branch declined (echo, or flag ON). `canvasOwned` false ⇒ the text path runs unchanged.
- **A pending subscribe is already owned.** `subscribedPaths.add(path)` runs at `plugin/src/files/canvas-sync.ts:324`, before the first `await` — documented at `plugin/src/main.ts:944-946`. There is no unowned window during a pending subscribe.
- **An excluded path is not shared at all.** Exclusion is manifest-level (`plugin/src/files/manifest.ts:302` → `isSharedPath` false) and `plugin/src/files/vault-events.ts:113` returns early for a non-shared path, so it reaches neither subsystem today and this is unchanged. PLAN's "exclusion pattern" branch of the open question is a **non-case**.
- **Handover ordering is load-bearing.** Unowned→owned calls `backgroundSync.unsubscribe(path)` on the statement immediately before `canvasSync.subscribe(path, role)`, in the same synchronous block: `unsubscribe` flushes the pending `Y.Text` write and detaches the observer (`plugin/src/files/background-sync.ts:148-156`), so the last text flush lands *before* CanvasSync's seed reads the file, and no vault event can interleave.
- **Trade-off, stated explicitly.** The fallback syncs a canvas as raw `Y.Text`, i.e. through the very character-merge mechanism that corrupts edges. It is accepted because (a) it engages only when there is no structured doc at all, (b) it is exclusive — never concurrent with `CanvasSync`, which is what causes the corruption, and (c) it is announced with `CANVAS TEXT FALLBACK:`. The rejected alternative — leave the canvas unsynced — is silent data isolation with no signal.

### 6.2 Persistence writer seams (WP7 — resolves PLAN open question 2)

This keeps `plugin/src/files/vault-events.ts:121`'s existing `canvasSync.isRecentDiskWrite(file.path)` check correct with **no change at the vault-events end**, and it is what stops the Part V "`lastWrittenContent` goes stale when the other writer changes the file" failure mode.

- **Architecture notes — the scope decision and why `remoteSeq` is not ported:**

  **Decision:** `CanvasPersistence` owns **scheduling as well as the byte-write**. `CanvasSync` stops writing `.canvas` bytes from the CRDT observer entirely. The `remoteSeq` counter and its gate are **not** ported — they are made unnecessary rather than duplicated.

  **Why the protected property survives.** The gate exists because `CanvasSync` snapshots the serialized content **early**: at debounce-timer fire it captures `seq` and `content` together (`plugin/src/files/canvas-sync.ts:711-714`) and then performs an `await ensureFolder(...)` before writing (`:780`). A remote delta integrated in that window would be clobbered by the older snapshot, so `writeToDisk` compares the captured sequence against the current one and yields — at `:774`, and again at `:783` after the await precisely because a delta can land during it.

  `CanvasPersistence` has no such window. `flushToDisk` serializes the doc **at flush time**, synchronously, immediately before the write (`plugin/src/files/canvas-persistence.ts:188`), with no interleaving `await` between snapshot and `io.write`. A stale snapshot therefore cannot exist. Its observer has no origin filter (`:138-141`), so *every* change — local capture or remote delta — re-arms the debounce, which means the final write in any burst always carries the newest doc state. The invariant "a flush never writes content older than the newest integrated delta" is preserved **structurally**, which is strictly stronger than a counter comparison.

  **Why not the alternative.** Keeping the debounce and the sequence gate in `CanvasSync` and delegating only the byte-write would preserve the early-snapshot shape that made the gate necessary, and would then require threading `expectedSeq` across a module boundary into a component whose stated contract is "downstream-only, observes the doc, knows nothing about the sync layer". More surface, a weaker invariant, and it leaves two components that both believe they schedule canvas writes. Rejected.

  **What must still be proven, not asserted:** AC3 exists because this argument is structural. Two residual windows are real and must be closed by AC6 — the `await io.write` itself (two overlapping flushes can resolve out of order, and `lastWrittenContent` is only assigned *after* the await at `:194`), and the absence of the `isPathSafe`/`ensureFolder` guarantees the retired writer provided.
