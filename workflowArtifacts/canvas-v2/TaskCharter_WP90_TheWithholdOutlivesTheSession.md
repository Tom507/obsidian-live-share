## 1. Task Objective

- **Outcome:** a record that a seed boundary refused, and whose deletion from the user's `.canvas` was therefore withheld, is **still there after a restart**. Today the withhold is a per-session, in-memory predicate; the next cold open takes `doc-wins`, never reads the file, and flushes the projection over it. **The record is gone — deleted as a consequence of a refusal**, which is I11 verbatim, one restart later.
- **Why durability and not a longer session scope, stated plainly because the alternative is the cheaper-looking answer:** **the invariant says *never*.** BUILD_SPEC I11 — *a refusal may withhold a write, it may never destroy one* — and `canvas-sync.ts:1424-1425` states it in the tree in those words. **A protection with a lifetime is not "never"; it is "not yet".** Widening the scope from "this session" to "this session plus N minutes", or to "until the plugin unloads", moves the moment of destruction without removing it, and leaves the user's data safe only for as long as nobody restarts Obsidian — which the product's own E2E installer does on every run. The only scope that satisfies an invariant phrased as *never* is one that outlives the process, and the lift WP63 already built (`isSeedRefusalResolved`, `canvas-sync.ts:1521`) is what stops that from becoming a permanent withhold.
- **Why it is P0-class in severity though it is chartered under P1.** It destroys **exactly the class of record the entire I11 invariant was created to protect** — a record the local model could not represent, which is by definition a record the user cannot get back from the doc, because it never entered the doc. Every other data-loss defect this run found destroyed something a resync could restore. This one destroys the only copy. The phase is **P1** because the mechanism is the ingest-schema boundary (BUILD_SPEC §5 PHASE P1, WP14/WP18/WP63) and that is where the charter belongs in the spec's own ordering; the **severity is P0-class and the Dispatcher has already ruled it so** (`DISPATCHER_STATE.md:1272`).
- **BUILD_SPEC reference:** `workflowArtifacts/canvas-v2/BUILD_SPEC_CanvasV2.md` — section 9, work package **WP90**; section 4.6 (invariant → work-package traceability, **I11**); section 5 PHASE P1 (WP63's component entry); section 7 (Quality Gates). Phase **P1**.

**The host is only accidentally safe, and the mechanism of the accident is exactly one `if`.** In session 2 a **host** runs `subscribe`'s `role === "host"` arm, which re-reads the file (`:2723-2726`), re-seeds, and **re-derives the same refusal** — so the ledger is non-empty by the time `attachCanvasPersistence` runs, and the `doc-wins` flush is withheld. *Acceptance evidence is **two LIVE Obsidian instances** driven through the E2E rig — `POST http://127.0.0.1:39431/command` (vault A) / `:39432` (vault B) — with headless rows carrying every case a live instance must not be abused to produce. **Blind sets are discontinued** — no `blind_set1`, no `blind_set2`, no falsification injection and no `BlindVerificationLedger` row is owed. **Every live row records the role its instance actually resumed as, quoted from its own `[session] resuming as …` line** (S37). `canvas.simulateEdit` and `canvas.open` are **never** called; every leaf is opened with `canvas.typeInNode{open:true}`, empty text, no blur. **No `data.json` value is read, printed, logged, hashed into a report or fixtured** — key names and boolean presence only.*

1. **The cascade is REPRODUCED RED on the unmodified tree, live, across a real restart, in the role where the accident does not save it.**
   - **Deliverable:** a live reproduction on a bundle with **the instrument and no fix**. Session 1: a `wp90-*` `.canvas` under `_liveshare-test/` carrying one valid record and one the ingest gate refuses. Session 2: **both Obsidian instances restarted** through the existing installer path, then the board cold-opened.
   - **Observable — session 1, the precondition, asserted and not assumed:** `SEED REFUSED:` is emitted for that path with the refused id and its reason; the refused id is **present in the user's `.canvas`** read through `canvas.file`; and the record is **absent from the doc**, read through `canvas.state`. All three, before the restart.
   - **Observable — session 2, the criterion:** `coldOpen` is shown to have taken **`doc-wins`** for that path (its own receipt, not inferred from timing); **no** `SEED REFUSED:` line appears for that path in session 2; and the refused id is **gone from the user's `.canvas`**. That is the RED.
   - **Observable — the role control (S37), and it is a positive control, not a repetition:** the same scenario is run with the peer resuming as **host**, where §3 Verification 3 predicts the file **survives** because producer A re-derives the refusal. **A run in which both arms destroy, or neither does, has not reproduced the defect** — it has found a different one, and it is reported as such.
   - **Vacuity risk — named:** the file surviving because **nothing was ever written**, rather than because it was protected — the `doc-wins` receipt and a `CANVAS WRITER:` line for that path are what distinguish them, and the guest arm must show the write **landed**. Second: the record never being in the file at the start of session 2 — asserted immediately before the restart, per-run id, never inherited from session 1's setup. Third: the doc arriving **empty** in session 2, which takes the `seeded-from-file` branch and re-derives the refusal for a completely different reason — `docNonEmpty` must be shown true. Fourth: the vacuity guard WP87 got wrong — *"the id is in the file"* checked by substring search over the whole `.canvas` matches `"x": 20` and `"width": 400`; the check parses the **record's own id field**. Fifth: **the suite is not idempotent by default** — scenarios that leave nodes behind let a re-run pass on the previous run's state (the first vacuity instance found in this E2E suite); per-run ids and a swept teardown are mandatory.

2. **A refusal recorded in session N still withholds in session N+1 — and the projection is UNTOUCHED, which is C17 AC3.**
   - **Deliverable:** the durable withhold. A refusal outlives the process and is consulted **before** the `doc-wins` flush can change the bytes.
   - **Observable (live, the GREEN of AC1's RED, same suite, same rig, opposite role assignment):** after the restart the refused id is **still in the user's `.canvas`**, `coldOpen` still returned **`doc-wins`**, and the withhold is **narrated** — the `SEED REFUSED:` signature (or its stated durable equivalent) is emitted in session 2 **without any seed having run**, so the withhold is *observable state and never a silent no-op*, which is WP63 AC2 carried forward verbatim.
   - **Observable (C17 AC3, headless, and this is the row that separates WP90 from Ä3):** for the **same doc state**, the bytes `serializeCanvas` produces are **byte-identical** with and without a standing durable refusal, and byte-identical to the pre-WP90 build. **Nothing is re-injected into the projection.** Asserted by comparing serializer output, not by reading the file — the file is withheld and therefore proves nothing about the serializer.
   - **Observable (structural):** `SeedRefusal`'s shape (`boundary`, `kind`, `id`, `reason`) is unchanged and no **user text, node content or `.canvas` payload** is persisted anywhere by the durable record — ids, reasons and boundaries only. A durable store that keeps a copy of the record's content **is** pass-through wearing a different coat.
   - **Vacuity risk — named:** a green produced by the write never being **attempted** — a flush must be shown to have been attempted and withheld, not merely absent. Second: a green produced by the **host's accidental re-seed** — the row runs in the role where producer A does **not** run, recorded from the peer's own resume line. Third: a "byte-identical projection" asserted against a doc that holds **no refused record at all**, which is trivially equal; the comparison runs on a doc state that has a standing refusal. Fourth: `withholdOnSeedRefusal` left `false` in the fixture, which makes `writeIsWithheld` return `false` at `:364` and every row green for the wrong reason (`canvas-persistence.ts:228` defaults it `true` — the fixture must be shown to be using the default).

3. **The lift still lifts — ACROSS a restart — and the withhold cannot become permanent.**
   - **Why this is a criterion and not a nicety:** `writeIsWithheld`'s own doc comment states it — *"a withhold that outlives its cause is its own data-loss class: a canvas stuck withheld stops persisting the user's real edits"* — and WP63's residual already names the case it cannot resolve. **Making the withhold durable makes that risk durable too**, and it is the single most likely way for this repair to be worse than the defect.
   - **Observable (live, across a restart):** with a durable refusal standing, the refused record is made valid — by a remote delta that creates it properly, or by the user repairing the file so the next seed admits it — and the **next write attempt** lifts the withhold, emits `SEED RESTORED:`, and the file resumes receiving the canonical projection. The lift is asked **on the write trigger, never on a timer** (WP63's landed discipline, reused, not re-implemented).
   - **Observable (the other exit, live):** the user **removes** the offending record from the `.canvas` outright. WP63's residual says the path then stays withheld until it is re-seeded; **a durable withhold must not make that state permanent.** The verdict here is reported either way: if the durable design resolves it, that is shown; if it does not, the residue is stated with the same honesty WP63 stated it, and it is **carried up**, not smoothed over.
   - **Vacuity risk — named:** demonstrating the lift **within** the session that recorded the refusal — WP63 already proves that (`test_tp03`), and repeating it proves nothing about durability. The row must **span a restart**. Second: a lift that fires because the durable record was silently dropped at startup rather than because the refusal resolved — the durable record must be shown **present** at session-2 start and **absent after** the lift. Third: driving the lift with a timer, which is the one shape `writeIsWithheld` forbids.

4. **The host's accidental safety is PINNED, or shown to be no longer needed.**
   - **Deliverable:** the dependence stops being an accident. Either (a) the durable record makes producer A's protective side effect irrelevant, demonstrated by a test in which the host arm is disabled at its seam and the host is **still** safe; or (b) the dependence is **pinned by a test that reddens** if the host seed stops filling the ledger.
   - **Observable:** the chosen half, executed. For (a): with `applyCanvasToYMaps` not run, a `doc-wins` cold open on a host still withholds. For (b): a test that fails when `applyCanvasToYMaps`'s `ledger.note(...)` is removed, with that failure **shown**, not asserted.
   - **Why it is in scope at all:** *"the host is accidentally safe"* is the Dispatcher's own words and the reason the item was ranked P0 rather than P1 — *"nothing pins it, so it is one refactor from being unsafe too."* A repair that leaves the accident in place has closed one arm of a two-arm defect.
   - **Vacuity risk — named:** a test that passes because the fixture **refuses nothing** — the refusal must be shown to have occurred before the safety row counts. Second: (b) satisfied by a test that pins the *existence* of the `note(...)` call by text search rather than by driving the behaviour — the run has been bitten by exactly that (the frozen import allow-list regex reads comments). Third: choosing (a) and demonstrating it only headless, where "the host arm did not run" is trivially arranged; the live counterpart is the role control AC1 already runs.

5. **WP63, WP30 and WP79 are left standing — and the durable record is unreachable by any peer.**
   - **Observable (WP63):** all four `plugin/src/__tests__/v2/wp63/**` files pass **byte-unmodified**, and `test_tp03…:129` — *"a re-seed of the path resets the refused set"* — is named explicitly in the report as having passed unmodified, with one sentence on why a durable withhold does not contradict it (a seed re-derives; durability governs the branch where no seed runs). **No §7 licence is taken.**
   - **Observable (WP30):** `canvasImportAvailability` still reads `hasRefusals()` and C30's ACs are unchanged. The **behaviour change** — `degraded` now reports correctly across a restart where it silently reported `false` — is stated in the report as a consequence, not discovered later.
   - **Observable (WP79):** no WP79 code path is changed; its I11 constraint continues to hold by WP79's own means.
   - **Observable (the boundary, and it is a security row):** the durable record is **local-only and unreachable by any peer** — asserted structurally: it is not a shared-folder path, not a manifest entry, not a file-op payload, not a CRDT field, and no code path from a remote message reaches it. **WP68 is unbuilt and its subject is that a peer-reachable write into `.obsidian/**` is a code-execution surface**; this WP must not open a second one.
   - **Observable (WP85's boundary):** `files/canvas-persistence.ts`'s diff is reported **line by line**, and the report states positively that the write queue, the mute refcount, the settle window, the debounce, `writeSnapshot` and `onWritten` are unchanged, and that the single-writer invariant and WP85's attach seam are untouched.
   - **Vacuity risk — named:** *"the WP63 tests pass"* asserted from a full-suite green without naming the four files and their counts — a suite green hides a file that was quietly edited to stay green. Second: *"unreachable by any peer"* asserted by inspection; it is a **derived** claim, and it is the one place in this WP where a reachability census earns its cost. Third: the byte-unchanged claims for `canvas-persistence.ts` stated in prose rather than produced by a diff that was actually run.

## 5. Constraints and Known Risks

- **The largest risk in this WP is that the repair is worse than the defect.** A durable withhold that cannot lift is a canvas that permanently stops persisting the user's real edits — and unlike today's version, restarting does not clear it. **AC3 is not optional and may not be deferred to a follow-up.** WP63's own `writeIsWithheld` comment states this risk in the tree; it is being made durable along with the protection.
- **The second largest is that a "durable" store is one more thing that can be wrong.** Whatever holds the refusal across a restart must be readable before the first `doc-wins` flush, must not be a second file→CRDT input, must not carry user content, must not be peer-reachable, and must not be able to strand a path forever. The charter deliberately does **not** name the mechanism — that is Worker 3's decision — but every one of those five is an AC.
- **`coldOpen`'s ordering is a contract.** `attachCanvasPersistence` (`canvas-persistence.ts:692-707`) states it: *"Ordering is the contract and it is not negotiable: `coldOpen()` runs AFTER the doc has synced"*, and `main.ts:2886` relies on `CanvasSync.subscribe` having already run. A durable read that happens before the ledger handle is created, or after the flush, is a repair that measures nothing.
- **The relay is production and shared** (`https://liveshare.neuralangels.de`), and it currently holds a live session (`sessions 1, documents 59, clients 2`, uptime ≈ 19.6 d as of 2026-08-05 12:40). `GET /healthz` is the only permitted interaction; **no room is created, deleted or mutated.** AC1's restarts must not be performed in a way that ends the owner's room.
- **`data.json` holds live credentials.** No value is read, printed, logged, echoed into a report, a commit message or a fixture. Key **names** and boolean presence only. The vaults already carry three `data.json` backups each (`.pre-v2-smoke`, `.wp88-b34.pre`, `.wp88-b34.armed`); none is touched.
- **Restarting Obsidian is this WP's core instrument and it is the most disruptive thing in the rig.** `liveshare_e2e_install.py` kills Obsidian, installs, sets ports and relaunches; a restart mid-run destroys any sibling's live state. Constraint 5 in §2 Ordering is a hard precondition, and the run takes the 30-second no-change watch over both shared trees before and after.
- **Every install is digest-guarded and marker-grepped.** **S46** has fired for real three times, most recently at 11:41 on 2026-08-05. Always set `LS_EXPECT_SHA256`, and grep the **installed** bytes for a marker unique to this batch's own change — a digest proves *which* build, not *whose*. **S57(installer)** is also live: a live instance once answered `unknown cmd:` for two scenarios though the installer had verified the digest minutes earlier. **Every install-then-measure in this run rests on that gap**, and it is more load-bearing here than usual, because this WP restarts the instances deliberately.
- **Rule 14:** never `git checkout --`, `git restore` or `git stash` a shared path; the instrument for a parked baseline is a **detached worktree**; commit with `git commit -o <paths>`; re-read `git status` immediately before **every** commit. WP37 ran `git stash push` on shared paths three times and the first is almost certainly the revert WP81 caught.
- **A detached-worktree unit run is 15 tests short** unless `server/node_modules` is linked as well as `plugin/node_modules`, and it reports the shortfall as **two failed files**, not as a smaller total. Any baseline this WP quotes states its environment.
- **The canvas E2E baseline is 21/21 and is recorded as schedule-dependent in five checks** (`8458167`). It is **not** 19/19 and **not** 13/18 — both measured the rig (**S45**, WP85). Whatever it reads at handover is recorded as a measurement with its band.
